# Web UI V5: job index and job pages

## Overview
- replace the dashboard (one job table, inspector drawer, run dialog with editing) with the V5 design the
  owner approved after review rounds with agy: an index grid of jobs and a full page per job, one top bar on
  both. Reference mockup: `/tmp/cronn-ux/mock/v5.html` (static HTML + JS on a fake data layer, served from
  `/tmp/cronn-ux/mock`; working files only, not part of the repo)
- problems solved: typical operations took several clicks through a drawer and a dialog; job state and run
  history were hidden until the inspector opened; the layout felt cramped and unrefined; a 5s poll that
  lands between press and release of a click swallows the click
- what the owner gets:
  - **top bar** on every page: brand (link to the index), host switcher, search that filters the grid on the
    index and jumps to a job from a job page, status filter pills with counts, live indicator, theme,
    gear menu (settings and about, keyboard shortcuts, logout)
  - **index grid**: status dot, name, history strip of the last 20 runs, readable schedule, last run, next
    run, Run or Stop per row; header sort on Job, Last run and Next run where the first click puts the
    nearest to now on top and a second click flips it; jobs without a value (never ran, disabled) stay last
    both ways
  - **job page** at `/jobs/{id}`: back to the list, previous/next job with "n of N", facts (schedule with
    an enabled switch, last run, next run, a 30-run history strip whose bars select a run), a command bar
    (editable command, date field only when the command has templates, Run now or Stop), the latest 50 runs
    and the selected run's output, live while it runs
  - **every run start is confirmed** in a dialog that shows the exact command, marks an edited command and
    shows the template date; Stop keeps its confirmation bound to the run's start time
  - a confirmed run opens the job page on that run's live output
  - keyboard shortcuts: `/` and ⌘K search, j/k, Enter, r, [ ], Shift+E, Esc, t, ?, arrow keys in the jump
    list
  - log pane with numbered lines, error lines highlighted, a live cursor while running, and a wrap toggle
  - below 1040px the pills and sort move into one filter/sort menu, so phones (no grid header) can still sort
  - light and dark themes; responsive down to phones
- unchanged contracts: `/api/v1/*`; `POST /api/jobs/{id}/run` and `POST /api/jobs/{id}/toggle` for callers
  without `HX-Request` (the owner's `cronn` skill uses curl); stop endpoints for non-htmx callers; auth,
  CSRF and the expired-session `HX-Redirect`

## Code-Quality Rules (HARD — verify against every task before marking complete)

These rules supplement project CLAUDE.md and are NOT optional. They are the gate for marking any task complete. If a rule is violated, the task is not done — refactor, re-test, then mark complete.

**Signatures (hard limits):**
- No function or method has 4+ parameters. `ctx context.Context` does not count toward the budget. If you need 4+, use an option struct (e.g., `type fooOpts struct { ... }`).
- No function or method has 4+ return values. Split the function into two single-purpose ones, or return a struct.
- Multiple adjacent same-type parameters (`oldLine, newLine int`) are a swap hazard — review whether they belong on a struct.

**Methods vs standalone helpers (project rule, hard):**
- If a function is called only from methods of a single struct, it MUST be a method on that struct. Calling pattern decides, not field access.
- Standalone helpers are reserved for: (a) constructors and entry points (`Parse...`, `New...`, `Decorate...`), (b) utilities shared by multiple unrelated types or by both standalone functions AND methods, (c) tiny cross-cutting helpers.
- Before adding any standalone helper, mentally walk its callers. If every caller is a method of one type, make the helper a method on that type.

**Visibility (private by default, hard):**
- Lowercase identifiers by default. Only export when an out-of-package caller exists.
- Exception (per CLAUDE.md): methods called by other structs in the same package CAN be exported for inter-component API clarity. This is the only exception. It does not extend to types, functions, constants, or variables.
- Before exporting any new identifier, grep for cross-package callers. If none, lowercase it.

**Comments (default: none, hard):**
- Default to writing no comments. Add one only when the WHY is non-obvious (a hidden invariant, a workaround, behavior that would surprise a reader).
- Exported items get godoc comments starting with the name. Unexported items get lowercase non-godoc comments — or no comment at all.
- Never describe WHAT the code does when the code itself is self-evident. Never write multi-paragraph comments on routine helpers.

**Per-task gate (before marking ANY checkbox complete):**
1. Formatter runs clean (`~/.claude/format.sh` or `gofmt -s -w` + `goimports -w`).
2. `golangci-lint run --max-issues-per-linter=0 --max-same-issues=0` reports zero issues.
3. `go test ./... -race` passes.
4. Scan the new code for the four rule classes above. Specifically:
   - Grep new function signatures: `grep -nE '^func.*\(.*,.*,.*,.*\)' app/<path>/*.go` — any hit with 4+ comma-separated params (excluding `ctx`) is a violation. Same for the return-value side.
   - For every new standalone helper, `grep -rn 'helperName(' --include='*.go'` and confirm at least one caller is NOT a method of a single type. If all callers are methods of one type, convert.
   - For every new exported identifier, grep cross-package. If no out-of-package hit, lowercase it.
5. Only after 1–4 pass: mark the task complete.

If a previous task shipped a violation (spotted later by user, reviewer, or yourself): fix it in the next commit BEFORE starting the next task. Do not let violations accumulate.

## Solution Overview
- **two pages, one top bar**: `GET /{$}` renders the index, `GET /jobs/{id}` renders the job page; each is
  its own template set (`layout.html`, the page shell with the top bar, + its page template + partials), so
  each defines `main` once. Template files have distinct base names (`ParseFS` keeps the last file of a
  given base name) and every `define` name is unique across `partials/*.html` (`html/template` silently
  lets a later definition replace an earlier one). Navigation between pages is plain links (full page
  loads); everything inside a page is htmx. `layout.html` has no `hx-boost` (today's `base.html:14` sets it
  on `<body>`): boosted links would swap pages over AJAX, re-run `ui.js` top-level code and stack its timers
- **one cutover**: the job page and the index ship in the same task. They share `layout.html`, `ui.js`,
  `style.css`, the output and dialog fragments and the template sets, so a job page added beside the old
  dashboard would have to work around `ui.js`'s inspector code, the old CSS class names and the old
  fragments, only to delete those workarounds one task later
- **list state travels in the URL**: links to job pages carry `filter`, `sort`, `rev` and `search` (the
  index search field's existing name); the job page uses them for previous/next and "n of N" and puts them
  back on the "All jobs" link. When the job is not in the filtered list (filter changed, job hidden by the
  search), previous/next and "n of N" use all jobs in crontab order. Cookies keep setting a fresh page's
  filter and sort as today; per-tab hidden inputs (`#filter-mode`, `#sort-mode`, `#sort-rev`) win over them
- **polls never replace what the user is pressing**: the index polls only its rows (`#rows`), never the
  header with the sort buttons; the job page polls only its facts part. Every self-polling fragment (rows,
  facts, live output, the `after` wait) carries the htmx filter `[!uiHeld]`, where `window.uiHeld` is true
  only while the primary mouse button is down (htmx evaluates filter symbols on the event, then on
  `window`, so a top-level `let` would never be seen); the next tick after release refreshes. Rows and facts
  also trigger on `refresh-jobs from:body`, so toggle, run and stop update the page at once. The facts poll
  returns the title (`#jtitle`: dot, name, badge), the command bar's action (`#runact`: Run now, Stop, or
  nothing for a disabled job or under `--web.disable-manual`) and the pill counts as OOB fragments; the
  command and date inputs are never swapped, so edits survive every poll. Pill buttons themselves are
  never swapped by a poll, only their count `<em>`s and `#match-count`; filter and sort POSTs swap the
  header and pills as their own response
- **selected run**: the output fragment carries the selection as a hidden input `selected-run`
  (`<exec id>` or `live:<start>`), as `run-output`/`live-output` do today. The facts poll and `/runs`
  `hx-include` it, so the bar and the runs-list row stay marked across polls. A bar or runs-list click is
  an `hx-get` of that run's output into the output pane; the response sends
  `HX-Trigger-After-Swap: run-selected`, on which facts and runs re-render with the new selection. No OOB
  from a polled element carries selection (repo CLAUDE.md: OOB from a replaced element is lost). The index
  strip's bars are plain links to the job page with `run=<key>`
- **run start**: the command bar (job page) or a row's Run (index) posts to `run-confirm`, which renders a
  confirmation dialog in `#dialog-slot` showing the exact command, an edited marker and the template date.
  Run once posts to the run endpoint with the list state as hidden fields. Every htmx acceptance gets
  `HX-Redirect` to `/jobs/{id}?after=<unix micro taken just before the trigger send>&<list state>`, built
  with `s.url` and `jobsQuery.values()` from the re-parsed request, never from raw values. The job page
  shows "starting…" and polls `live-output?after=` every 1s. Each answer looks for the earliest manual run
  of that job (manual: the service sets `ExecutedCommand` for manual runs only) with start ≥ `after`,
  among active runs and among recorded ones (`JobRuns`), before applying the 10s limit, so an overlapping
  scheduled run is never mistaken for the started one and a run that already finished is still found. A
  found run is answered with its normal live or recorded output fragment plus `HX-Replace-Url` without
  `after` and `HX-Trigger-After-Swap: run-selected`, so a reload or a theme `HX-Refresh` never re-enters
  waiting. With none 10s after `after`, the pane says the run did not start and to check the cronn log,
  and the response stops polling with status 286 (htmx's stop-polling code). Rejections re-render the
  dialog with the error, as today
- **command field**: `readonly` only when command editing is off (`!CommandEditEnabled`); a disabled job
  keeps it editable, its `#runact` shows no Run, and `checkRun` still rejects a run of a disabled job.
  State that changes at runtime (enabled, running) lives only in `#runact`. Typing marks the field and
  date as edited and relabels Run to "Run edited"; Enter in either field submits the command bar form
- **run history**: two store methods return run summaries without the output column: `RecentRuns(limit)`
  for every job in one batched query (index strips, 20), `JobRuns(jobID, limit)` for one job (facts strip,
  30; the `after` match). The runs list keeps `GetExecutions(id, 50)` and re-renders on `runs-changed`,
  which the facts poll sends when the newest-run marker it gets from the client (`newest`: the newest active
  run's `live:<start>`, else the newest recorded run's id) differs from its own
- **sort direction**: `jobsQuery` gains `reverse`; `sortJobs` flips only the order between jobs that have a
  value. For last run that excludes never-ran jobs; for next run it excludes disabled jobs and jobs without
  a next time (`loadJobsFromCrontab` sets `NextRun` for disabled jobs too, so zero time alone does not
  cover them). Both groups stay last in both directions; reversed crontab order is the reverse of
  `SortIndex`. Keeping disabled jobs last under next run changes today's order, which sorts them by their
  unused next time; it ships with the V5 header sort
- **log pane**: the server renders output as one element per line, a CSS counter numbers them, lines
  matching `ERROR` or `fatal` (case-insensitive) get an error class, a running run ends in a blinking
  cursor; wrap is a checkbox in the log bar styled by `:has()` (no JS, not persisted)
- **narrow screens**: below 1040px the pills are replaced by one `<details>` menu holding the filter list
  with counts and the sort choices with their direction; below 720px the grid header is hidden and rows
  become two-line cards, so that menu is the only sort control there
- **menus** (host, gear, filter/sort) are `<details>`; one `ui.js` listener closes an open menu on an
  outside click or Esc
- removed from today's UI: the inspector drawer and its wide/wrap/overlay/inert machinery, the
  `#selected-job` hidden input, the failing-jobs alert banner (the Failing pill carries the count), the
  footer (version and links move into the settings dialog), the editable run dialog (editing moves into the
  command bar)

## Technical Details

**Routes after the change** (all behind `authMiddleware`; POSTs keep CSRF):
- `GET /{$}` index page; `GET /jobs/{id}` job page (404 page with a link to the index for an unknown id;
  `run=<exec id>` is checked to belong to the job, as `handleRunOutput` does, and ignored otherwise)
- `GET /api/jobs` rows fragment plus OOB pill counts and `#match-count`; `POST /api/sort-mode` and
  `POST /api/filter-mode` set cookies and render the rows, the header (sort arrows) and the pills;
  `rev` travels like `sort`
- `GET /api/jobs/jump?q=` jump list for the job-page search: jobs whose name or command contains every word
  of `q`, first 10
- `GET /api/jobs/{id}/facts?newest=&selected-run=` facts fragment (schedule, switch, last, next, strip)
  plus OOB `#jtitle`, `#runact` and pill counts; `HX-Trigger: runs-changed` when `newest` differs; a job no
  longer in the crontab gets a "removed from the crontab" notice, no Run/Stop, and status 286
- `GET /api/jobs/{id}/runs?selected-run=` runs list fragment with the selected row marked
- `GET /api/jobs/{id}/executions/{exec_id}/output` and `GET /api/jobs/{id}/live-output?start=|after=`
  output fragments for the job page (log lines, log bar with wrap, hidden
  `selected-run`), answering `HX-Trigger-After-Swap: run-selected`
- `POST /api/jobs/{id}/run-confirm` (form: `command`, `date`, list state) confirmation dialog, replacing
  `run-form`. POST keeps an edited command out of URLs, which the request logger and proxies record; 403
  under `--web.disable-manual`; an edited command is refused with the existing 403 when command editing is
  off
- `POST /api/jobs/{id}/run`: htmx acceptance → 202 + `HX-Redirect` as above; htmx rejection → 200 with
  `run-confirm` re-rendered with the error; non-htmx unchanged
- `POST /api/jobs/{id}/toggle` (htmx gets a toast, curl unchanged), stop-form, stop, theme, settings,
  neighbors: unchanged contracts, new markup
- removed: `GET /api/jobs/{id}/inspector`, `GET /api/jobs/{id}/run-form`; they 404 through the router like
  any unknown path

**Data**
- `persistence.RunSummary`, struct only, `db` tags like `ExecutionInfo`: `ID int` (`id`), `JobID string`
  (`job_id`), `StartedAt`, `FinishedAt time.Time` (`started_at`, `finished_at`), `Status enums.JobStatus`
  (`status`), `ExitCode int` (`exit_code`), `Manual bool` (`manual`, computed as
  `COALESCE(executed_command, '') != ''`; the column is nullable in the original schema)
- `(s *SQLiteStore) RecentRuns(limit int) (map[string][]RunSummary, error)`: one query,
  `ROW_NUMBER() OVER (PARTITION BY job_id ORDER BY started_at DESC, id DESC)`, rows `<= limit`
- `(s *SQLiteStore) JobRuns(jobID string, limit int) ([]RunSummary, error)`:
  `WHERE job_id = ? ORDER BY started_at DESC, id DESC LIMIT ?` on the existing index
- both added to the web `Persistence` interface (consumer side), mock regenerated
- `jobsQuery` gains `reverse bool`
- `(s *Server) getSortReverse(r *http.Request) bool`: form `rev`, then cookie `sort-rev`, then false
- `(s *Server) setSortCookie(w http.ResponseWriter, mode enums.SortMode, reverse bool)` writes both cookies
- `(s *Server) sortJobs(jobs []persistence.JobInfo, mode enums.SortMode, reverse bool)`; the failing-alert
  call (`handlers.go:149`) passes false until Task 2 removes it
- `(s *Server) listQuery(r *http.Request) jobsQuery`: the one parser of `search`, `filter`, `sort`, `rev`
  (form, then cookie, then default), replacing the inline `jobsQuery` literals in the handlers
- `(q jobsQuery) values() url.Values`: the list state for links; job links are
  `s.url("/jobs/"+id) + "?" + q.values().Encode()`, the back link `s.url("/") + "?" + ...`

**View models** (unexported types, exported fields because templates read them)
- `indexRow`: `Job persistence.JobInfo`, `Strip []stripBar`, `Link string` (job URL with list state)
- `stripBar`: `Key string` (exec id or `live:<start>`), `Class string` (ok, fail, run, empty), `Height int`
  (percent, scaled by duration against the longest shown run, with a floor so short runs stay visible),
  `Tip string` (time, result, duration, manual), `Href string`; built by
  `(s *Server) stripBars(req stripReq, q jobsQuery) []stripBar` with
  `stripReq{Job persistence.JobInfo, Runs []persistence.RunSummary, Size int}` (reads `s.activeRuns` for
  the live bar and `s.url` for links; pads with empty placeholders up to `Size`: 20 index, 30 job page)
- `TemplateData` (rendered by the layout on both pages) gains `Rows []indexRow` in place of `Jobs` and
  `Reverse bool`; keeps the top bar fields, counts and the `ManualDisabled`, `StopEnabled`,
  `CommandEditEnabled` flags
- `jobPosition`: `Pos`, `Total int`, `Prev`, `Next string` (links), built by
  `(s *Server) jobPosition(id string, q jobsQuery) jobPosition` from the same search → filter → sort as the
  index, falling back to all jobs when `id` is not in that list; named apart from `neighbors.go`, which is
  the host switcher
- `jobPageData`: embeds `TemplateData` and `jobPosition`; `Job persistence.JobInfo`, `Strip []stripBar`,
  `Runs []persistence.ExecutionInfo`, `Selected string`, `BackLink string`, `After int64`,
  `HasTemplates bool` (date field shown only then)
- `runConfirm`: `JobID`, `Name`, `Command`, `Date string`, `Edited bool`, `Error string`, `List url.Values`
  (list state echoed as hidden fields), replacing `runForm`

**`ui.js` after the change** (each where htmx has no attribute):
- `window.uiHeld`: set on primary-button `pointerdown`, cleared on `pointerup`, `pointercancel`, `blur`,
  `contextmenu` (window, capture); read by every poll filter. A click needs press and release on the same
  element, and htmx cannot defer a swap
- blink: toggles `blink-off` on `<html>` every 600ms; running dots, the live strip bar and the log cursor
  fade on it. A CSS animation restarts on each swap, so dots in freshly polled rows would blink out of
  phase with the rest of the page
- dialogs: `uiDialogSwapped`, `uiDialogClosed` (kept); focus restore on close targets the opener's id
- live output scroll keeping (kept, re-bound from `#inspector` to the job page's output pane): follow new
  lines only when already at the end
- tooltips: one `#tip` element under the hovered `[data-tip]` (history bars, copy icon), flipped above near
  the bottom edge, filled with `textContent`; the native `title` delay is too slow for scanning bars
- copy command: the icon in the command field copies the field's value with `navigator.clipboard` and
  shows a toast; there is no htmx attribute for the clipboard
- edited marking: on `input`, mark the command and date fields when they differ from the job's command
  (kept in `data-orig`) and relabel Run; htmx has no client-side comparison
- menus: close an open `<details>` menu on an outside click or Esc
- scroll the selected runs-list row into view after `run-selected`
- keyboard map (Task 3): `/` and ⌘K focus search; on the index j/k move a cursor row (kept across row swaps
  by job id), Enter opens it (in the search field: the first match), r opens its run confirmation; on a
  job page j/k go to next/previous job, [ ] select newer/older run, r opens the run confirmation, Shift+E
  toggles the schedule, Esc returns to the list (not from inputs or open dialogs); t theme; ? shortcuts
  dialog; in the jump list ↑↓ move, Enter opens, Shift+Enter opens the run confirmation. Keys act by
  clicking the existing htmx elements, so every key goes through the same requests as the mouse
- `data-keynav` focus-ring gate and `uiPollDone` (now driving the live indicator) kept
- removed: `uiSyncInspectorButtons`, `uiToggleInspectorMode`, `uiSetCovered`, `uiSyncCovered`,
  `uiInspectorSwapped`, `uiCloseInspector`, `uiRestoreFocus`'s inspector fallback

**Security**: untrusted input reaching the new code is the job id path value (looked up in the job map,
404 when unknown); the query and form values `search`, `q` (jump list), `filter`, `sort`, `rev`, `run`,
`selected-run`, `newest`, `after`, `start` (enums parsed with fallback to defaults, integers parsed with
errors answered 400, an exec id checked to belong to the job, text escaped by `html/template`); and the
command and date of the confirmation (displayed escaped, sent by POST; the run endpoint's existing `checkRun`
still decides, including the command-edit flag). Redirect and replace URLs are built from `s.url` and
re-parsed values only. No new capability: no new file, network or command path; the run and stop endpoints
keep their checks
